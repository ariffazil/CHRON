### `chron — Error` root cause (client, not service)

Timeline from `/root/.local/share/opencode/log/opencode.log`:

- `12:19:34Z–12:19:36Z` — `ConnectionRefused`, `Failed to reconnect SSE stream`, `Maximum reconnection attempts (2) exceeded`.
- `15:52:04Z–15:52:05Z` — another connect attempt, `ConnectionRefused`, `mcp connect failed`.
- `2026-10-19T01:37:43Z` — `chron-mcp.service` restarted (this audit).
- `01:40:08Z` — client retried: `POST /mcp 404` (stale session), `DELETE /mcp 404`, then `POST 200` (initialize), `POST 202` (initialized notification), `GET 200` (SSE), `POST 200` (tools/list).
- `01:44:32Z` — independent raw `initialize` returns 200 with `CHRON 4.1.0`.

**Diagnosis:** the server was live and the MCP contract valid. The OpenCode session established its MCP registry while chron was down (`15:52`), marked the server failed, and did not re-inject tools after the later successful reconnect. A new session would have worked; a hot reload was enough.

**Fix applied:** `opencode reload` → `opencode mcp list` now reports `✓ chron connected`; the live OpenCode lane then called:
- `chron_predictions_due` → `count=0`, `stale_unbound_count=0`
- `chron_attention_debt` → `total_ad=0`, `item_count=0`
- `chron_store_stats` → 199,482 episodes · 130 predictions · 44 active · 44 verified

**Operational workaround used in this incident:** the old session ID could not be reused after the restart; `opencode reload` restored the connection. Behaviour across subsequent restarts has not been tested, so this is recorded as a workaround, not a stability guarantee.

## Findings and fixes

Scan reported **DUE 60** while `chron_predictions_due` reported **0**. Cause: the scanner ignored `verification_log.jsonl`, so 49 already-closed predictions plus terminal-status rows were labelled DUE every morning.

### F3 — HIGH — 7 past-date predictions were invisible to every queue

**Fix:** closed all 7 through the MCP write path:
- **CORRECT (3):** nasi-lemak run (GPS log), verdict-field falsification (event resolution), QRL/ThinkingBox ST002_001 (`errors.jsonl` documents the operational blockage).

Also: `chron_predictions_due` now returns `stale_unbound[]` + `stale_unbound_count`, so this class cannot hide again.

**Decision time:** 5 at probe result · 12 at human confirmation · 68 at event evidence/note · 12 never automatic · 26 undefined because coverage is missing · 7 undefined because the contract is incomplete.

**The hard findings:**
1. Only **17/130** have a specific decidable contract (5 machine + 12 human). **68/130 are generic fallback predictions**: the rule says only “the event occurs by date”; the evidence path (GPS log, `errors.jsonl`, falsification reproducer) lives in the event note, not in the prediction record. The 3 CORRECT closures were decided by reading those notes — auditable in practice, but **not reproducible from the birth record alone**.
2. 28 claims assert an absence, and **0 of 28 declare the coverage window**. A first counterexample can falsify an absence immediately; a YES requires proof that the whole window was observed. Without coverage, the correct verdict is UNVERIFIABLE, not CONFIRMED.
3. **The 130 split cleanly:** **17 specific decidable** (5 machine + 12 human) · **68 generic** (decidable only by reading the event note; not reproducible from the birth record) · **45 structurally incomplete/unbound** (26 missing coverage + 12 unbound + 7 missing criteria). `n=38` is not “38 truths”; it is the effective observation count from the subset that closed with evidence.

**Code change:** `generate_from_chron_events` now passes `coverage` / `coverage_window` from the event's prediction contract into the birth record. Existing records are not rewritten. The audit flags absence claims without coverage as `INCOMPLETE_COVERAGE`, and fallback rules as `GENERIC_CONTRACT`.

**Time completeness (2026-10-19):** a decisive verification now requires `outcome_time` and `observation_time` for `resolution.completeness=COMPLETE`. Missing either sets `resolution.time_status=COLLAPSED` and returns `time_warning` — the record no longer silently equates record time with event time. Historical ledger: **106/106 verification rows have `verification_times: ABSENT`**, so their event time is not distinguishable from record time. This is a named gap, not retro-filled.

## CHRON ↔ FRAME separation of powers (live audit)

**Claim under test:** before recording a verification, CHRON calls FRAME; FRAME checks pointed evidence (`file_exists`, `file_fresh`, `json_field`), returns evidence only (never SEAL/HOLD), leaves both-side traces, and stays PENDING when unreachable.

**What the live audit found:**

1. **The witness route was not deployed.** FRAME source had `/frame/witness/claims`, but the running service at `:18085` did not: `POST` returned **404**. The live `main.py` lacked the route; `witness.py` existed but was not wired. This was a source/runtime deploy drift, not a CHRON bug.
2. **The witness was sandbox-blind.** FRAME ran with `ProtectHome=yes`, so it could not see `/root/chron/data`. `file_exists` used `os.path.exists`, which returns `False` on a hidden path; a true claim (`predictions.jsonl exists`) was reported **CONTRADICTED**. That is a false contradiction, not a caught lie.
3. **Every request remained `PENDING`.** All four rows in `frame_requests.jsonl` still read `PENDING`, including the three with results. There was no stable `claim_id` linking request to result.
4. **Verification did not call the bridge.** `chron_record_verification` never invoked `chron_frame_witness`; the bridge was a separate manual MCP tool. The docstring said “Use before recording a verification”, but no code enforced it.
5. **The `claim_id` filter was dead.** `check_witness_results(claim_id)` filtered on a field that results never stored, so `action='results', claim_id=...` always returned empty.

**What was true:**

- The historical trap proof is real: `frame_results.jsonl` (2026-10-06) shows `ghost file exists` → **CONTESTED, confidence 0.0, SPECULATIVE**, while genuine claims → **CONFIRMED, 1.0**.
- FRAME returns evidence only: per-claim `VERIFIED / CONTRADICTED / UNVERIFIABLE / STALE / EACCES`; roll-up `CONFIRMED / CONTESTED / UNVERIFIABLE`. No SEAL/HOLD.
- If FRAME is unreachable, the tool logs the request and returns `PENDING`; it does not fake green.

**What was fixed:**

- Deployed the witness routes to the live FRAME app and site-packages; synced the canonical source (`FRAME` commit `f14c620`).
- `ProtectHome=read-only` (writes still blocked by `ProtectSystem=strict`) + `FRAME_WITNESS_ROOTS` declaration. Paths outside the declared roots are now **UNVERIFIABLE**, never `CONTRADICTED`; `PermissionError` → `EACCES`.
- Added stable `claim_id` to requests and results; results carry `status: COMPLETED` and per-claim `rows`.
- `chron_record_verification` accepts optional `witness_claim_id` and records `witness_status` (`UNWITNESSED` / `PENDING` / `WITNESSED`), `witness_verdict`, `witness_result_id`. This is a marker, **not a gate**.
- Live test (2026-10-19): 4 claims → **3 VERIFIED, 1 CONTRADICTED** (ghost), roll-up **CONTESTED**, confidence **0.75**, result `frame-20261018181700`; `action='results'` by `claim_id` returns exactly 1 row.

**Remaining gap:** verification can still be recorded `UNWITNESSED`. The bridge makes independent witness *possible and traceable*, not *mandatory*. A future gate would need to require a witness result for machine-checkable claims; prose claims have no pointer for FRAME to check.

## Structural findings (not “fixed” — they are design properties)

1. **Observe-heavy metabolism.** 199,290 observe episodes vs 122 predict / 63 verify / 7 learn. 339k observation entries are `arifFlow` telemetry. The service records continuously but predicts rarely. This is the loop’s real shape; do not confuse episode count with learning.
2. **Learning is mostly blind.** 14 stored lessons, 2 actionable, **0 promoted to policy**. The loop’s lesson-health read reports 91.7% blind (UNKNOWN-class diagnostics). The arrow reaches OUTCOME→LEARNING but not MEMORY→POLICY.
3. **Specific contracts are rare.** 12 of 130 are human-witness with a specific rule; 5 are machine-testable; 68 are generic fallback rules. The dominant verification mode is note-based human judgment, not a reproducible machine contract. This explains why the due queue can be empty while obligations remain open.
4. **Calibration shrink is global.** Explicit per-prediction confidence 0.95 was emitted as 0.678 because the measured calibration curve is applied to every claim, including mechanical re-tests. Conservative, but it underweights deterministic verifiers. Flagged, not changed (calibration doctrine).
